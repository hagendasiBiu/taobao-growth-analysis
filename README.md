# 淘宝 App 用户增长与转化分析

基于阿里云天池公开历史日志的电商用户行为分析实训，使用 Python、Pandas 和 MySQL 分析流量、购买、短期复购及运营机会。

本项目重点回答：**流量增长是否同步带来购买？如何基于用户行为提出可验证的运营策略？**

分析数据覆盖 **2017年11月25日至12月3日**。项目初始分析完成于2026年9月，核心指标在2026年10月复盘重算。项目使用过AI辅助编程和分析整理；结论以明确定义和明细核对为依据。它是公开数据实训，不代表淘宝公司的内部项目或线上运营效果。

## 核心结果

| 指标 | 结果 | 口径 |
|---|---:|---|
| 清洗后行为日志 | 4,966,986条 | pv、fav、cart、buy四种事件合计 |
| 样本用户 | 49,396人 | 九天内有保留行为的去重用户 |
| 商品浏览PV | 4,447,807次 | pv事件数 |
| 购买用户 | 33,620人 | 九天内有buy事件的去重用户 |
| 购买行为 | 99,755次 | buy事件数，不直接等同订单数 |
| 跨日购买用户比例 | 54.98% | 至少两个不同自然日购买的18,485人 / 33,620名买家 |
| 活跃与购买高峰 | 20、21、22点小时桶 | 九天累计PV和buy的前三小时桶，覆盖20:00至22:59:59 |

周末与工作日按日均比较：

| 指标 | 工作日日均 五天 | 周末日均 四天 | 增幅 |
|---|---:|---:|---:|
| PV | 457,673.0 | 539,860.5 | 17.96% |
| 全行为活跃用户 | 36,097.2 | 41,928.5 | 16.15% |
| 购买事件 | 10,861.4 | 11,362.0 | 4.61% |

样本中周末流量增长快于购买事件增长，可作为进一步拆解用户结构、类目结构与购买路径的线索。只有九天、两个周末，不能据此断定周末导致购买意愿下降。

## 分析流程

1. 分块读取原始CSV，按 `user_id % 20 == 0` 选择用户，保留入选用户的源记录。
2. Unix秒时间戳转为 `Asia/Shanghai`，限制九天观察窗口，检查字段完整性与行为类型。
3. 构造日期、小时、星期、周末标记，计算活跃、购买、复购和留存。
4. 使用SQL表达指标，并用Pandas对清洗明细独立重算。
5. 输出每日、小时、留存及历史分群汇总，提出待实验验证的运营假设。

按用户抽样比逐条抽行为更能保留行为序列，但固定ID取模不是严格随机保证，仍需考虑ID规则与样本代表性。

## 复现步骤

建议使用Python 3.10或以上版本；完整复算需自行下载数据，预留磁盘和内存。核心核对脚本需要同时在内存处理约500万条记录，内存不足时应先改为数据库或分块聚合实现。

```bash
python -m pip install -r requirements.txt
```

从[阿里云天池淘宝用户购物行为数据集](https://tianchi.aliyun.com/dataset/649)下载并解压 `UserBehavior.csv`，放入 `01_raw_data/`。原始文件无表头：

```text
user_id,item_id,category_id,behavior_type,timestamp
```

遵守数据源条款。仓库不再分发原始日志、抽样或清洗明细，只提供代码与汇总结果。

从仓库根目录运行：

```bash
python scripts/prepare_data.py
python 08_project_review/audit_project.py
```

第一条命令生成 `02_processed_data/UserBehavior_clean.csv`，若目标已存在则停止，防止覆盖。预期抽样4,969,753条，过滤到4,966,986条；第二条命令写出日、小时、首次观测留存与JSON核对结果。汇总CSV可以不下载原始数据直接查看。

可选MySQL流程：在本地MySQL 8执行 `03_sql/01_schema.sql`；按 `.env.example` 将变量设置到当前进程环境（示例文件不会自动加载）；再运行：

```bash
python scripts/load_mysql.py
```

导入要求目标表为空，避免重复导入；CSV的date映射为behavior_date，datetime映射为behavior_time。导入完成后可执行 `02_basic_metrics.sql`、`03_behavior_coverage.sql` 和 `04_analysis_queries.sql`。

`legacy_indexes.sql`是历史加索引脚本，**不要在新建schema后重复执行**。历史可视化Notebook部分查询依赖未完整留档的数据库中间表，不作为一键复现入口。MySQL流程提供了代码和配置说明，尚未完成本次发布版本的数据库端执行验证。

## 口径与局限

- **事件与订单**：buy是购买行为，没有order_id、支付金额、毛利或广告成本，不能计算真实GMV、客单价、ROI或LTV。
- **复购**：54.98%指观察窗口内至少两个自然日购买，不是每个人首购后都观察完整九天的复购率。
- **留存**：历史留存CSV统计某日所有活跃用户之后是否回来；新增首次观测队列结果另存，两者不能混称注册新客留存。
- **漏斗**：原Notebook使用手填漏斗数，生成查询没有留存。公开Notebook已移除该图和相应手填汇总。按“同一用户同一商品存在浏览→收藏/加购→购买严格时间顺序”重算，三阶段为3,528,090、55,988、5,123对，见查询与核对脚本。
- **分群**：历史汇总表保留作过程记录，但原打标规则与逐人标签未完整保存，尚不能完整复现20.98%、13.06%、11.74%等标签占比。不把行为频次直接解释为经济价值或已确认流失。
- **展示**：`05_tableau/`是展示用CSV，当前仓库不包含完整Tableau工作簿。

## 运营建议与验证思路

围绕收藏或加购但未购买的用户，可设计提醒、相关商品承接及小额权益等方案；高活跃时段可作为触达排期假设。高意向不等于优惠券带来的高增量，应通过用户级随机实验比较不干预、提醒、提醒加券三组，观察完整窗口内的购买率差异，并结合补贴、触达成本、退款和毛利评价经济性。

这些是**待验证的策略建议**，没有在真实平台实施，也没有证明GMV或ROI提升。

## 验证状态

核心结果已在本地清洗明细中用Pandas核对，历史每日行为和次日活跃回访人数与已有CSV一致。发布整理时对新增分块预处理做了小样本边界验证，并检查了发布文件中的凭据和个人路径。依赖范围并非完整锁定环境，历史Notebook亦未在全新环境中逐格执行。详见 [复现和修订记录](docs/reproducibility.md)。

## 新增 离线名单策略验证

已补充按时间切分、验证集选规则、后续窗口评估的[离线策略验证](09_offline_validation/README.md)。固定1,000人容量下，主测试覆盖281名后续买家，同池随机名单理论期望213.22名；名单命中率28.10%对随机期望21.32%，相对高31.79%。周末后续窗口相对高28.78%。3项时间边界测试及独立CSV流式实现交叉核对通过。

这些指标评价未来买家识别，不能称为干预后真实转化率提升。按加购次数排序在主测试覆盖289名买家，略高于验证集选定的最近意向规则，故不宣称策略最优。代码、全部基线、容量情景及待实施的真实实验方案见上述目录。
